# 네이버 검색 노출 온보딩 운영 체크리스트

> **전제**: 코드 레벨 준비물(사이트맵·RSS·소유확인 meta·IndexNow)은 모두 구현 완료 — 이 문서는 운영 절차만 다룸.
> **대상**: 신규 인스턴스(`{slug}.onwell.site` 파생 서브도메인 또는 커스텀 도메인) 발행 후 네이버 검색 노출까지의 운영자 체크리스트.
> **주의**: 네이버 서치어드바이저는 **호스트 단위**로 관리한다. 인스턴스별 서브도메인과 커스텀 도메인은 각각 별도 사이트로 등록해야 한다.

---

## 0. 코드 레벨 확인 사항

| 항목 | 확인한 파일 | 운영 의미 |
|---|---|---|
| 사이트맵 | `apps/web/src/app/(site)/[instanceSlug]/sitemap.xml/route.ts` | `siteBaseUrl(instanceSlug)` 기준으로 인스턴스별 `sitemap.xml`을 동적 생성한다. 커스텀 도메인이 있으면 canonical host 기준 URL이 들어간다. |
| RSS | `apps/web/src/app/(site)/[instanceSlug]/rss.xml/route.ts` | 네이버 RSS 제출용 `rss.xml`을 인스턴스별로 생성한다. published article 최대 50건을 최신순으로 포함한다. |
| robots | `apps/web/src/app/(site)/[instanceSlug]/robots.txt/route.ts` | 인스턴스별 robots.txt가 `Sitemap: ${siteBaseUrl(instanceSlug)}/sitemap.xml`을 출력한다. |
| 소유확인 meta | `apps/web/src/app/(site)/[instanceSlug]/layout.tsx` | `clinic.naverSiteVerification` 값이 있으면 `<meta name="naver-site-verification">`이 전 페이지 head에 출력된다. |
| IndexNow | `apps/web/src/lib/indexnow.ts` | `NODE_ENV !== "development"`, `VERCEL_ENV === "production"`, `NAVER_INDEXNOW_KEY` 설정, canonical origin 계산 성공 시 네이버 IndexNow와 공용 IndexNow 엔드포인트로 제출한다. |

## 1. 온보딩 체크리스트

### 1.1 호스트 확정

| 체크 | 담당 | 시점/주기 | 작업 | 검증 방법 |
|---|---|---|---|---|
| [ ] | 운영자 | 인스턴스 발행 직후 | 네이버 서치어드바이저에 등록할 최종 호스트를 확정한다. 예: `{slug}.onwell.site` 또는 커스텀 도메인. | 운영표에 `host`, `instanceSlug`, 도메인 유형(서브도메인/커스텀)을 기록했다. |
| [ ] | 운영자 | 커스텀 도메인 전환 시마다 | 커스텀 도메인은 기존 서브도메인과 별개의 새 호스트로 서치어드바이저에 신규 등록한다. | 서치어드바이저 사이트 목록에 새 커스텀 도메인이 별도 사이트로 보인다. |

커스텀 도메인 전환 시 서브도메인 → 커스텀 도메인 301과 canonical 일관성은 `lib/custom-domains.ts` 단일 SoT 기준으로 코드가 자동 처리한다. 단, 네이버 서치어드바이저 등록은 자동 이전되지 않으므로 새 호스트를 반드시 신규 등록한다.

### 1.2 네이버 소유확인

| 체크 | 담당 | 시점/주기 | 작업 | 검증 방법 |
|---|---|---|---|---|
| [ ] | 운영자 | 호스트 확정 직후 | 네이버 서치어드바이저에서 사이트를 추가하고 `naver-site-verification` 토큰을 발급받는다. | 서치어드바이저 소유확인 화면에 meta token이 표시된다. |
| [ ] | 운영자 | 토큰 발급 직후 | 어드민 의원정보에 `naver-site-verification` 토큰을 입력한다. | `clinic_profile.naverSiteVerification` 값이 저장되어 있다. 해당 필드는 migration C0051에서 추가된 값이다. |
| [ ] | 운영자 | 토큰 저장 후 | 공개 사이트 head에 meta가 출력되는지 확인한다. | `https://<host>/`의 HTML head에 `<meta name="naver-site-verification" ...>`가 보인다. |
| [ ] | 운영자 | meta 확인 후 | 서치어드바이저에서 소유확인을 완료한다. | 서치어드바이저에서 사이트 소유확인 완료 상태가 보인다. |
| [ ] | 운영자 | 소유확인 완료일 기준 매년 | meta 태그 방식은 1년마다 재인증이 필요하므로 만료일을 운영 캘린더에 등록한다. | 캘린더에 재인증 예정일과 담당자가 등록되어 있다. |

현재 구조는 HTML 파일 방식이 아니라 meta 태그 방식이다. HTML 파일 방식은 갱신이 불필요하지만, 현 구조에서는 1년 만료 캘린더 관리가 필요하다.

### 1.3 사이트맵 제출

| 체크 | 담당 | 시점/주기 | 작업 | 검증 방법 |
|---|---|---|---|---|
| [ ] | 운영자 | 소유확인 완료 후 | 네이버 서치어드바이저에 `https://<host>/sitemap.xml`을 제출한다. | 서치어드바이저 사이트맵 제출 목록에 `https://<host>/sitemap.xml`이 보인다. |
| [ ] | 운영자 | 제출 직후 | 브라우저에서 사이트맵 URL을 직접 확인한다. | XML이 열리고 `<urlset>`과 인스턴스 canonical URL 목록이 보인다. |

사이트맵은 인스턴스별 동적 생성이다. 커스텀 도메인이 연결된 경우 사이트맵 URL도 커스텀 도메인 기준이어야 한다.

### 1.4 RSS 제출

| 체크 | 담당 | 시점/주기 | 작업 | 검증 방법 |
|---|---|---|---|---|
| [ ] | 운영자 | 사이트맵 제출 직후 | 네이버 서치어드바이저에 `https://<host>/rss.xml`을 제출한다. | 서치어드바이저 RSS 제출 목록에 `https://<host>/rss.xml`이 보인다. |
| [ ] | 운영자 | 제출 직후 | 브라우저에서 RSS URL을 직접 확인한다. | RSS XML이 열리고 `<rss>`, `<channel>`, 최신 article `<item>`이 보인다. |

RSS 제출은 네이버 전용 요구로, 사이트맵 제출과 병행한다.

### 1.5 웹 페이지 수집 요청

| 체크 | 담당 | 시점/주기 | 작업 | 검증 방법 |
|---|---|---|---|---|
| [ ] | 운영자 | 사이트맵·RSS 제출 후 | 서치어드바이저 `[요청 > 웹 페이지 수집]`에서 주요 URL을 수동 요청한다. | 요청 결과 화면에서 제출 URL의 요청 완료 상태가 보인다. |
| [ ] | 운영자 | 대량 발행일마다 | 사이트당 1일 50 URL 한도를 넘지 않도록 우선순위를 정한다. | 당일 요청 URL 수가 50개 이하이고, 우선순위 URL부터 제출되어 있다. |

대량 발행 시 우선순위는 신규 Pillar 페이지와 주력 키워드 아티클을 먼저 둔다. IndexNow는 보조 수단이므로 수집 요청을 대체하지 않는다.

### 1.6 IndexNow 자동 제출 확인

| 체크 | 담당 | 시점/주기 | 작업 | 검증 방법 |
|---|---|---|---|---|
| [ ] | 개발 | production 배포 전 | production 환경에 `NAVER_INDEXNOW_KEY`를 설정한다. | production 환경 변수에 `NAVER_INDEXNOW_KEY`가 존재한다. |
| [ ] | 개발 | production 배포 후 | 발행/갱신 시 IndexNow 자동 호출 조건을 확인한다. | `NODE_ENV !== "development"`, `VERCEL_ENV === "production"`, key 설정, canonical origin 계산 조건을 만족한다. |
| [ ] | 개발 | cron 운영 시작 후 | cron 재제출이 IndexNow batch 제출 경로를 사용하도록 확인한다. | 재제출 결과에 submitted URL 수와 host가 관측된다. |

IndexNow는 색인을 보장하지 않는다. 수집 요청·사이트맵·RSS를 보완하는 신호로만 취급한다.

### 1.7 스마트플레이스 연계

| 체크 | 담당 | 시점/주기 | 작업 | 검증 방법 |
|---|---|---|---|---|
| [ ] | 운영자 | 사이트 발행 후 | 네이버 스마트플레이스에 홈페이지 URL을 등록한다. | 플레이스 화면에 `https://<host>/` 홈페이지 링크가 보인다. |
| [ ] | 운영자 | 홈페이지 URL 등록 시 | 스마트플레이스와 사이트의 주소·전화·진료시간 NAP을 완전히 일치시킨다. | 플레이스와 사이트의 주소, 전화, 진료시간 문구가 동일하다. |
| [ ] | 운영자 | 플레이스 정보 확보 후 | 어드민에 `clinic.metadata.naverPlace`의 `placeId`, `placeUrl`을 입력한다. | 공개 사이트 JSON-LD `sameAs`에 네이버 플레이스 URL이 자동 반영된다. |

스마트플레이스 → 홈페이지 URL 등록은 역방향 연결이다. 사이트 → 플레이스 연결은 어드민 `clinic.metadata.naverPlace` 입력 후 JSON-LD `sameAs`로 반영된다.

### 1.8 색인 대기 및 진단

| 체크 | 담당 | 시점/주기 | 작업 | 검증 방법 |
|---|---|---|---|---|
| [ ] | 운영자 | 등록 후 14~16일 | 색인 반영을 기다린다. | 네이버 검색 또는 서치어드바이저에서 색인 URL 수 변화가 확인된다. |
| [ ] | 운영자 | 등록 후 정기 확인 | 서치어드바이저 "사이트 진단" 리포트를 확인한다. | 다운로드 크기/시간, 페이지 오류, robots/사이트맵 설정, 색인 URL 수를 확인하고 이상 항목을 운영표에 기록했다. |

등록 후 통상 색인 소요는 14~16일이다. 이 기간 중에도 사이트 진단 리포트는 정기 확인한다.

## 2. 완료 기준

| 완료 항목 | 완료로 보는 상태 |
|---|---|
| 서치어드바이저 사이트 등록 | 대상 호스트가 사이트 목록에 별도 등록되어 있다. |
| 소유확인 | meta 방식 소유확인이 완료되어 있다. |
| 사이트맵 제출 | `https://<host>/sitemap.xml` 제출 기록이 있다. |
| RSS 제출 | `https://<host>/rss.xml` 제출 기록이 있다. |
| 웹 페이지 수집 요청 | 우선순위 URL이 1일 50건 한도 내에서 요청 완료되어 있다. |
| IndexNow | production 환경에서 key와 게이트 조건이 충족되어 자동 제출 가능 상태다. |
| 스마트플레이스 | 플레이스 홈페이지 URL, NAP 일치, JSON-LD `sameAs` 반영이 완료되어 있다. |
| 진단 모니터링 | 사이트 진단 리포트 확인 일정과 담당자가 운영표에 등록되어 있다. |

## 3. 반복 운영 캘린더

| 주기 | 담당 | 반복 작업 | 검증 방법 |
|---|---|---|---|
| 매일 | 운영자 | 서치어드바이저 웹 페이지 수집 요청 한도 확인. 사이트당 1일 50 URL 이하로 신규 Pillar·주력 키워드 아티클부터 요청한다. | 당일 제출 URL 목록과 제출 수가 운영표에 기록되어 있다. |
| 정기 | 운영자 | 서치어드바이저 "사이트 진단" 리포트 확인. 다운로드 크기/시간, 페이지 오류, robots/사이트맵 설정, 색인 URL 수를 점검한다. | 리포트 확인일, 이상 여부, 후속 조치가 운영표에 기록되어 있다. |
| 매년 | 운영자 | meta 태그 방식 소유확인 재인증. | 소유확인 완료일 기준 1년 만료 전 재인증 일정과 완료 기록이 있다. |
| 발행/갱신 후 | 개발 | `NAVER_INDEXNOW_KEY`와 production 게이트 하에 IndexNow 자동 제출 및 cron 재제출 상태를 확인한다. | 제출 결과 또는 로그에서 submitted URL 수와 host를 확인할 수 있다. |
| 커스텀 도메인 전환 시 | 운영자 | 새 호스트를 서치어드바이저에 신규 등록하고 소유확인·사이트맵·RSS·수집 요청을 다시 수행한다. | 새 커스텀 도메인이 서치어드바이저 사이트 목록에 별도 등록되어 있다. |
