## 검토 관점

### 1. cycle1 patch 수용 정합

- LL-01~LL-25 각 patch 가 본문에 반영되었는지 + 의도된 효과 (impact 해소) 가 충족되었는지.
- 일부 patch 가 본문/비범위 표/시나리오/cascade 한쪽에만 반영되어 다른 섹션과 어긋나지 않는지.
- patch 가 새로운 SoT 충돌 (특히 ARCH § 3.8.1 의 reservationChannels 상속 · DATA_MODEL C-21 의 representativeDoctors 자동 매핑 표) 을 만들었는지.

### 2. LL-01 의 schema 정합

- `location_profile.clinic_profile_id` composite FK + `slug='main'` row 만 NOT NULL CHECK — 향후 다지점 (slug ≠ 'main') 의 clinic_profile_id 정책 (NULL 허용 vs NOT NULL 전 row) 결정?
- ClinicProfile.locations[] 동적 구성의 cardinality 보장 (1 main row 강제) — INSERT 순서 정합 (LL-ACTION-04 의 ClinicProfile → LocationProfile 순서 ↔ FK DEFERRABLE INITIALLY DEFERRED 가 같은 tx 안 가능?)?
- C-01 required `locations[] >= 1` 의 Git 출력 시 빌드 실패 (1 main row 누락) 가능성 — Server Action 단일 tx 가 모두 함께 upsert 하므로 항상 1 row 보장? race 시?

### 3. LL-02 의 상속 모델

- `LocationProfile.metadata.reservationChannelsInheritedFrom = "clinic_profile.primary_ctas"` marker 만 저장 → Git 빌드 시 ClinicProfile.primary_ctas 직접 reference. 다지점 합류 시 (지점 별 reservationChannels override) 의 hybrid 모델 cascade marker 부재?
- `primary_ctas` JSONB array 형식 — 어떤 CTAConfig (CT-03) 필드를 채워야 하는가? `@id`, `type`, `value`/`url`, `availableFor` 등의 minimal subset 명시?
- 빌드 시점 dynamic reference — `featuredChannelId` 가 primary_ctas[].id 와 일치하지 않는 경우 빌드 무시 (DATA_MODEL C-21 v0.6 의 규약 정합)?

### 4. LL-05 의 BusinessHours 변환

- form 의 7요일 단순 입력 (mon~sun 각 행) → server action 안 `convertToOpeningHoursSpec()` 가 동일 (open, close) 행을 grouping 해서 `openingHours[]` 1 spec 으로 합치는 로직 — round-trip (저장 → 조회 → 다시 form 화) 안정성? grouping 깨질 때 7요일 individual spec 으로 fallback 결정?
- `receptionHours` 와 `lunchBreaks` 의 form 입력 — v0.2 의 form 명세 LL-FORM-07 에는 "점심" 1행 입력만 있고 `receptionHours` 입력 필드 자체가 없음. 그렇다면 receptionHours 는 빈 배열 (CT-02 SoT optional 허용)?
- `specialClosures[]` v0.2 빈 배열 의도 — DATA_MODEL 의 휴진/공휴일 표현이 빈 배열로 충분? 명시 marker?

### 5. LL-08·09 partial UNIQUE 결정

- `legal_document_instance_5type_unique WHERE document_type IN ('privacy','terms','non-covered','refund','complaint')` — 향후 cookie/other 가 5종으로 추가될 때 partial unique 정의 변경 cascade marker?
- partial unique 의 WHERE 절이 CHECK 가 아니라 INDEX 술어 — 자동 생성 시점에 row 가 5종 중 1개여도 unique 검출되는가 (postgresql 의 partial unique 정의 동작 정합)?

### 6. LL-12·LL-19 의 운영자 메시지

- skeleton CHECK 위반 4종 (status_skeleton_limit · published_at_null · risk_level_skeleton_limit · main_clinic_required) 의 매핑이 모두 mapDbErrorToResult cascade — error 종류별 운영자 안내 한국어 메시지가 일관 (정중 + 후속 단계 명시)?
- `legal_document_status_skeleton_limit` 의 메시지 "후속 검수 단계 합류 후 가능합니다" — 정확한 운영자 행동 가이드? 시점/책임 명시?

### 7. LL-15 의 form (d) 5 record

- form (d) UI 가 5 record × effectiveDate input — name 충돌 (`effectiveDate.privacy` 등 dot notation) 해결 방안? FormData 의 multi-field naming + zod schema 의 Record 처리?
- 5 record 별 effectiveDate 의 default = policyEffectiveDate — 운영자가 (c) 의 policyEffectiveDate 만 입력하고 (d) 미입력 시 5 record 모두 동일 값. 운영자가 (c) 미입력 + (d) individual 일부만 입력 시 (c) required 위반 (LL-FORM-04 의 4 필드 required) 이 우선 — 명시?

### 8. LL-17 audit 7 row emit

- ADMIN_UI_SKELETON_PLAN cycle v1.2 audit emit best-effort 패턴 (single emit) → v0.2 의 7 row emit — 1 row 실패 시 나머지 6 row 의 atomic 정합?
- LegalDocument row 의 payload 추가 필드 (`documentType` · `templateVersion`) — 기존 통일 shape (`{contentType, slug, mode, status, originalSlug}`) 의 확장. analytics consumer 호환?
- `LocationProfile` 의 `status: null` — ClinicProfile 의 null 과 동일. v0.2 단계 LocationProfile/ClinicProfile 은 status 없음 명시?

### 9. LL-CASCADE 정합

- LL-CASCADE-01 (ARCH § 3.8.2 변수 화이트리스트 reference) — ARCH 본문에 표 신설 vs link only? 본 plan v0.2 acceptance 이전에 ARCH 패치하면 SoT 인덱스 순서 정합?
- LL-CASCADE-02 (ADMIN_UI_SKELETON_PLAN § 5.5 audit matrix) — 기존 1 row (ClinicProfile) → 7 row 로 확장. Plan v1.0 acceptance status 위배?
- LL-CASCADE-03 (CONTENT_STANDARDS § 7 예외) — § 7 의 다른 예외 (FAQ · ReviewPolicy 등) 와 동일 형식? 면제 범위 (answer-first AST · 표현 검사 · 변수 검증) 가 각 룰 마다 정확 정의?
